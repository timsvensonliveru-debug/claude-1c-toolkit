# ManageEngine ServiceDesk Plus: коннектор API v3

`scripts/servicedesk.py` читает заявки и создаёт заявку по шаблону через [API v3 ServiceDesk Plus](https://www.manageengine.com/products/service-desk/sdpod-v3-api/) (разделы requests и request_templates). Только стандартная библиотека Python, без MCP и сторонних пакетов.

## Подключение (один раз)
1. В профиле пользователя ServiceDesk Plus сформируйте ключ: раздел **API Key generation**. Права ключа: чтение, создание заявок и заметок.
2. В `.env` (шаблон `.env.example`, сам `.env` не коммитить) задайте две переменные:
   - `SD_BASE_URL` адрес портала до `/api/v3` (для облачной версии вместе с `/app/<портал>`);
   - `SD_API_KEY` ключ из шага 1.
   Необязательно: `SD_AUTH_SCHEME` (`authtoken` по умолчанию, ключ в заголовке `authtoken`; `oauth` отправляет `Authorization: Zoho-oauthtoken ...`), `SD_CONFIG` путь к конфигу шаблонов и групп. Заголовок `authtoken` проверен на рабочем портале (локальная установка), для облачных порталов с OAuth задайте `oauth`.
3. Скопируйте `config/servicedesk.example.toml` в `config/servicedesk.toml` и впишите имена шаблонов и групп. Обычный ключ часто не читает списки шаблонов и групп (ошибки 403 и 404), поэтому имена берутся из конфига, а не запрашиваются.

Ключ нигде не печатается и не сохраняется, в сообщениях об ошибках его нет. Адрес должен быть `https` (внутренний узел по `http` только при `SD_ALLOW_HTTP=1`), узел можно закрепить переменной `SD_ALLOWED_HOSTS` (через запятую), перенаправление на другой узел отклоняется.

## Чтение заявок
```bash
python scripts/servicedesk.py list --group "Поддержка" --status Open --since 2026-10-01 --until 2026-10-21 --limit 300
python scripts/servicedesk.py list --technician "Имя Исполнителя" --json
```
Фильтры соединяются через AND и собираются в `list_info.search_criteria` (поля `group.name`, `status.name`, `technician.name`, `created_time`). **Проверено на рабочем портале 22.10.2026:** `list`, фильтр по группе (`group.name`) и по дате (`--since`) работают. Не проверены `--status` и `--technician` (имена полей и значения статусов сверьте с вашим порталом), создание заявки не проверялось. Свои условия: `--criteria-json файл` (массив объектов `search_criteria`, добавляются к фильтрам). Выгрузка постраничная: `start_index` растёт на `row_count`, пока `has_more_rows`, не больше `--limit` записей, размер страницы `--page-size` (до 100).

Вывод по умолчанию: номер, тема, статус, группа, приоритет, шаблон, время создания. **Структурные поля заявителя и исполнителя и вложения не выводятся** без флагов `--with-people` и `--with-attachments`. Тема и описание выводятся как есть и могут содержать ФИО, почту, телефон или номера договоров: проверьте их на персональные данные перед тем, как показывать модели.

## Создание заявки по шаблону
```bash
python scripts/servicedesk.py create --template access_request --subject "Доступ к базе" --description "..." --group support
```
По умолчанию **сухой прогон**: печатается тело запроса, ничего не отправляется. Отправка только с `--send` и только после ручного подтверждения: команда показывает тело и просит ввести слово `отправить`. Без интерактивного терминала отправка отказывает. Подтверждение защищает от случайного запуска, но не является механизмом авторизации: процесс с терминалом и доступом к окружению его автоматизирует. Запускайте отправку сами (в сессии агента с префиксом `! `), а ключу выдайте только нужные права.

## Сверка по факту: meta и create --check
Имя шаблона, группы и техника проверяется по порталу, а не по памяти:
```bash
python scripts/servicedesk.py meta --what templates     # все шаблоны (id и имя), постранично
python scripts/servicedesk.py meta --what technicians --name Фамилия   # техники по части имени (имя в портале полное)
python scripts/servicedesk.py meta --what observed      # группы и приоритеты, реально стоящие в последних заявках
python scripts/servicedesk.py create --check --template ... --subject ... --group ... --technician ... --priority ...
```
Что читает обычный ключ (проверено на рабочем портале 23.10.2026): шаблоны (`requests/template`) и пользователи (`users`) читаются; группы, приоритеты, категории, срочность, влияние и список `technicians` закрыты (403), адрес `groups` отдаёт 404. Поэтому `--check` сверяет шаблон по списку портала, техника поиском по имени (сервер не фильтрует пользователей по роли, роль проверяется на клиенте), группу по наличию хотя бы одной заявки с такой группой, приоритет по последним заявкам. Пустой вывод замечаний означает, что имена существуют, а не что заявка корректна по содержанию. Только чтение, ничего не создаётся.

## Техник и приоритет по умолчанию
В конфиге `[defaults]` задаются `technician` и `priority`, в `[technicians]` псевдонимы техников, значение шаблона в `[templates]` может быть числом (тогда это id шаблона). Аргументы `--technician` и `--priority` перекрывают значения по умолчанию. Имя техника в портале пишется полностью (фамилия, имя, отчество); у человека бывают две учётные записи (заявитель и техник), назначать нужно техническую, `--check` подскажет похожие имена. Реальные имена и шаблоны своей компании хранить в приватном конфиге, не в публичном репозитории.

## Заметка к заявке
```bash
python scripts/servicedesk.py note --request 123456 --text "комментарий"          # сухой прогон
python scripts/servicedesk.py note --request 123456 --text "комментарий" --send   # после ручного подтверждения
```
По умолчанию заметка внутренняя (заявителю не показывается, техник уведомлением не дёргается), `--visible-to-requester` меняет это. Порядок отправки тот же, что у создания: сухой прогон, затем `--send` и слово `отправить` в интерактивном терминале.

## Отправка без терминала (агент по решению человека)
Для среды, где нет интерактивного терминала (агент через удалённый узел), отправка идёт по файлу решения. Включается только человеком: `SD_AGENT_SEND=1` в окружении, без неё файл решения отклоняется.
1. Сухой прогон печатает тело и его `sha256`.
2. Человек, увидев тело, записывает решение: `servicedesk.py approve --digest <sha256> --by "Имя" --out решение.json`.
3. `servicedesk.py create ... --send --approve-file решение.json` (то же для `note`).
Решение привязано к цели и телу (для заметки это номер заявки и текст), любое изменение делает его недействительным; у каждого решения свой `approval_id`; живёт два часа и гасится один раз атомарно (метка в каталоге `~/.cache/ai_toolkit_sd_approvals`, путь `SD_APPROVAL_LEDGER`) до отправки, при ошибке отправки возвращается для повтора. Если каталог недоступен для записи, отправка отменяется. Два параллельных запуска с одной темой и заявителем блокируют друг друга. Это защита от ошибки и повтора, а не механизм авторизации: процесс с доступом к окружению файл может записать сам. Решение принимает человек, агент его себе не пишет.
Перед отправкой команда ищет заявку с той же темой и тем же заявителем за последний час и останавливается (`--allow-duplicate` снимает остановку; без `--requester-id` совпадением считается одна тема, остановка консервативная). Заявитель передаётся структурой по id: `--requester-id` или `[defaults] requester_id` в конфиге. После создания заявка читается обратно и сравнивается с запросом (шаблон, группа, приоритет, техник, заявитель, тема), расхождения печатаются.

## Кто создаёт заявку в боевом портале
Создание заявки и заметки в боевом SD выполняет человек, либо агент только по явному решению человека, принятому для этой заявки. Агент готовит тело и прогоняет `create --check`, показывает человеку, отправку подтверждает человек. Права ключа: чтение, создание заявок и добавление заметок. Ключ получается в профиле техника портала (раздел генерации ключа API), права ключа равны правам этого техника в роли, отдельной настройки у ключа нет. Нужно право записи, роль техника должна разрешать создание заявок и заметок.

## Ограничения
- Имя шаблона и группы должны точно совпадать с именем в портале. Для шаблонов с обязательными полями (заявитель, категория) добавьте эти поля в шаблон портала, а не в команду.
- Время периода (`--since`, `--until`) считается по UTC, границы дня сдвиньте при необходимости.
- Облачные порталы разных регионов отличаются адресом, проверьте `SD_BASE_URL` по документации портала.
